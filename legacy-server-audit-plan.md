# План диагностики и восстановления Doctor Farmer на `193.233.201.76`

## Цель

Провести контролируемый функциональный аудит самостоятельного экземпляра Doctor Farmer по адресу `http://193.233.201.76:3000`, исправить блокирующие настройки развёртывания и подтвердить работоспособность ключевых сценариев: входа, доступа сотрудников, хозяйств, КП, заявок, обращений и тестирования.

## Установленные причины неполной работы

| Наблюдение | Причина | Последствие |
|---|---|---|
| Кнопка «Вход владельца кабинета» не работает | На сервере не заданы параметры OAuth (`OAUTH_SERVER_URL`, `VITE_APP_ID` и связанные настройки). | Вход владельца через Manus OAuth не может быть запущен. |
| Сервер открыт только по `http://193.233.201.76:3000` | OAuth использует защищённую cookie состояния; для обычного внешнего HTTP-адреса она не передаётся. | Даже при добавлении OAuth-параметров вход через владельца на этом IP будет ненадёжным и должен работать только за HTTPS. |
| Нет `.env`, переменной `DATABASE_URL` и активной MySQL/MariaDB | Самостоятельный сервер не получил конфигурацию базы данных из управляемой среды. | Нельзя выполнить миграции; сохранение хозяйств, КП, заявок, доступа и обращений не будет работать надёжно. |
| Логи содержали ошибку `%VITE_ANALYTICS_ENDPOINT%` | На сервере не были настроены переменные аналитики, но шаблон пытался загрузить незаполненный URL. | Ошибка маршрутизации Express; строка удалена вручную и приложение успешно пересобрано. |

> Самостоятельный сервер — отдельная среда. GitHub передаёт исходный код, но не переносит автоматически переменные окружения, базу данных, OAuth-секреты и файловое хранилище управляемого приложения.

## Решение, которое требуется выбрать перед исправлением

| Вариант | Что будет сделано | Когда подходит |
|---|---|---|
| **A. Полноценный самостоятельный сервер** | Настроить HTTPS-домен, отдельную MySQL/TiDB-базу, файловое хранилище и все серверные переменные; применить миграции и проверить OAuth. | Если именно IP/домен сервера должен быть основным рабочим кабинетом команды. |
| **B. Использовать опубликованный кабинет** | Использовать `https://docfarmerqui-4txfmjap.manus.space` как рабочую версию с уже настроенными базой, хранилищем и OAuth. Внешний сервер оставить только как техническую копию или выключить. | Если важнее немедленная работа без отдельной серверной инфраструктуры. |
| **C. Независимый вход владельца без Manus OAuth** | Доработать код: создать отдельный безопасный механизм владельческого доступа на самостоятельном сервере и не зависеть от OAuth Manus. Всё равно потребуется HTTPS и база. | Если нужно навсегда отказаться от Manus OAuth на самостоятельном сервере. |

Для варианта A или C потребуется безопасно передать или создать инфраструктурные реквизиты. Их нельзя брать из GitHub или публиковать в репозитории.

## Фазы работ

### 1. Проверить актуальное развёртывание

На сервере последовательно проверить `git status`, ветку, `pm2 status`, последние журналы и ответ локального порта 3000. Подтвердить, что `doctor-farmer` запущен из `/root/doctor-farmer-quiz` и использует свежую production-сборку.

### 2. Закрыть ошибку служебной аналитики в исходном репозитории

Ручное удаление незаполненного Umami-скрипта на сервере перенести в GitHub отдельным проверенным коммитом. Это предотвратит возврат ошибки `%VITE_ANALYTICS_ENDPOINT%` при следующем `git pull`.

### 3. Настроить среду и доступ

В зависимости от выбранного варианта создать защищённый файл окружения вне GitHub и передать его в `pm2`. Для самостоятельного полного контура в нём должны быть отдельные значения подключения к базе, криптографического секрета сессий, URL OAuth при использовании OAuth, параметры S3-совместимого хранилища и разрешённый внешний origin. Для OAuth сначала подключить HTTPS-домен; plain HTTP IP не использовать для рабочего входа.

### 4. Применить миграции без тестовых данных

После проверки строки подключения к отдельной базе выполнить миграции Drizzle. До выполнения проверить, что это нужная база, а резервная копия или снимок данных существует. Не создавать фиктивные хозяйства, заявки или обращения для теста.

### 5. Полный функциональный аудит

Проверить в отдельных гостевой, сотруднической и административной сессиях следующий набор сценариев.

| Сценарий | Ожидаемый результат |
|---|---|
| Гость | Может просматривать публичные материалы; `/farms`, `/proposals/new`, `/order-requests`, `/support` и `/quiz` не раскрывают рабочие данные/тесты. |
| Вход владельца | Кнопка запускает корректный безопасный вход только при выбранной и настроенной стратегии авторизации. |
| Заявка доступа и код | Сотрудник может запросить доступ, администратор видит заявку и выдаёт одноразовый код; повторное использование и истёкший код блокируются. |
| Хозяйства и КП | Сотрудник видит только свои хозяйства и КП; администратор видит данные команды только в панели администратора. |
| Заявки на поставку | Сохранение, печать и история отгрузок работают с owner-scoped доступом. |
| Обращения | Отправка с поддерживаемым вложением сохраняет только метаданные в БД, файл — в хранилище; сотрудник не видит чужие обращения, администратор обрабатывает общую очередь. |
| Тестирование | Без регистрации показывается экран доступа; после входа доступны задания. |
| Экспорт и печать | Excel и печатная форма создаются без ошибок и без раскрытия чужих данных. |

### 6. Контроль после исправлений

Выполнить `pnpm check`, `pnpm test`, `pnpm run build`, перезапустить `pm2`, проверить журналы только после свежего запуска и открыть внешний HTTPS-адрес без кэша. Зафиксировать результаты и создать контрольную точку перед передачей.

## Риски и меры защиты

| Риск | Мера |
|---|---|
| Копирование секретов в GitHub | Хранить значения только в серверном `.env` или защищённой конфигурации `pm2`; не выводить их в терминал и не отправлять в чат. |
| Применение миграций к неверной БД | Перед миграцией проверять хост/имя БД без раскрытия пароля и иметь резервную копию. |
| Вход на HTTP IP | Не использовать OAuth на plain HTTP; сначала настроить HTTPS-домен или применить независимую стратегию входа. |
| Повторное появление ошибки аналитики | Зафиксировать удаление незаполненной служебной строки в репозитории и пересобрать после обновления. |
| Раскрытие рабочих данных | В каждом сценарии отдельно проверять гостевой доступ и owner-scoped правила сотрудника/администратора. |

## Критерий завершения

Самостоятельный сервер считается готовым, когда он работает по HTTPS, использует явно настроенные собственные сервисы базы и хранения, позволяет владельцу безопасно войти, а все сценарии таблицы аудита проходят без ошибок и без раскрытия данных между сотрудниками.
